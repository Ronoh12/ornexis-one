# SPRINT 010 — DOCUMENT MANAGEMENT FOUNDATION

## Status

COMPLETE

---

## Objective

Establish the secure, tenant-aware Document Management foundation for
ORNEXIS ONE.

Sprint 010 introduces the first reusable platform capability for storing,
retrieving, organizing, securing, and auditing organization documents and
files.

The implementation must provide a stable foundation for future capabilities
including:

- Contact attachments
- Employee documents
- HR records
- CRM documents
- Service Desk attachments
- Procurement documents
- Supplier documents
- Financial documents
- Workflow attachments
- Organizational knowledge
- Compliance records
- Records management
- Document versioning
- Expiry and obligation management
- Enterprise search
- Industry-specific document repositories

The Document domain must remain organization-scoped, permission-aware,
storage-provider-independent, auditable, and secure by default.

# Architectural Principles

The Document Management foundation must follow these principles:

1. Documents always belong to an Organization.
2. Document queries must always be tenant-scoped.
3. Document access must require explicit permissions.
4. Physical file storage must be separated from document metadata.
5. Storage implementation must be abstracted behind a provider interface.
6. Local filesystem storage is permitted for development.
7. Database records must never depend directly on machine-specific absolute paths.
8. File names supplied by users must never determine physical storage paths.
9. Stored file names must be generated by the platform.
10. Upload and download operations must be auditable.
11. Branch and Department assignments must preserve organization integrity.
12. Document metadata must remain useful independently of the physical storage provider.
13. File validation must occur before persistence.
14. File deletion must be controlled and auditable.
15. Cross-tenant document access must return no document information.

# Organization Structure Assignment

branchId

Optional.

departmentId

Optional.

A document may belong to:

- the organization generally
- a branch
- a department
- a branch and department

Any referenced Branch or Department must belong to the same Organization as

Cross-tenant structure assignment must be rejected.

# Local Storage

Sprint 010 implements local development storage.

Default conceptual root:

uploads/

Recommended organization isolation:

uploads/
  organizations/
    {organizationId}/
      documents/
        {generatedFileName}

The exact physical path must be generated by the Local Storage Provider.

The database stores a relative storageKey rather than the machine-specific
absolute path.

# Upload Middleware

Sprint 010 requires multipart/form-data support.

Introduce an upload middleware dependency suitable for Express.

The middleware must:

- accept a single file
- enforce maximum file size
- reject missing files
- prevent arbitrary client-controlled storage paths
- expose validated file metadata to the controller
- avoid permanently storing rejected files

Storage orchestration remains under application control.

# File Validation

Initial allowed file categories should support common organizational
documents.

Recommended MIME types:

application/pdf

image/jpeg
image/png

text/plain
text/csv

application/msword

application/vnd.openxmlformats-officedocument.wordprocessingml.document

application/vnd.ms-excel

application/vnd.openxmlformats-officedocument.spreadsheetml.sheet

The validator must reject unsupported MIME types.

File extension must also be normalized and validated.

The system must not trust the client-provided filename alone.

Executable and script uploads must not be allowed during Sprint 010.

Examples to reject include:

.exe
.bat
.cmd
.ps1
.sh
.js

Additional content inspection and malware scanning are future security
extensions.

---

# File Size Validation

Maximum file size must be configurable.

Initial default:

10 MB

Oversized uploads must be rejected before document metadata is persisted.

---

# File Checksum

Generate:

SHA-256

for every successfully uploaded physical file.

Store the checksum in:

checksumSha256

This establishes a foundation for:

- integrity verification
- duplicate detection
- security analysis
- future versioning
- storage migration verification

Sprint 010 does not automatically reject duplicate checksums.

# POST /documents

Required permission:

documents.upload

Content type:

multipart/form-data

Expected fields:

file
title
description
branchId
departmentId

Required:

file

title may default to a safe normalized representation of the original
filename if not explicitly supplied, but explicit title support must exist.

Successful upload:

1. Authenticate user
2. Resolve organization context
3. Verify documents.upload
4. Validate multipart request
5. Validate file size
6. Validate MIME type
7. Validate extension
8. Validate branch
9. Validate department
10. Validate branch/department relationship
11. Generate stored filename
12. Generate storage key
13. Persist physical file through Storage Service
14. Generate SHA-256 checksum
15. Create Document metadata
16. Create audit event
17. Return Document metadata

If database persistence fails after the physical file was stored, the
application must attempt to remove the orphaned file.

---

Required permission:

documents.view

Returns organization-scoped document metadata.

Must never return physical machine paths.

Supported query parameters:

search
status
branchId
departmentId
mimeType

title
description
originalFileName

All filtering remains organization-scoped.

---

# GET /documents/:id

Required permission:

documents.view

Returns metadata for one organization-owned Document.

Cross-tenant IDs must behave as:

Document not found

rather than exposing foreign document existence.

---

# GET /documents/:id/download

Required permission:

documents.download

Flow:

1. Authenticate
2. Resolve organization
3. Verify permission
4. Resolve organization-owned Document
5. Resolve storage provider
6. Resolve storage key
7. Read physical file through Storage Service
8. Create audit event
9. Stream/send file securely

The API must not accept an arbitrary filesystem path from the client.

Recommended download headers include:

Content-Type
Content-Disposition
Content-Length

The original filename may be used for Content-Disposition after safe
sanitization.

---

# PATCH /documents/:id

Required permission:

documents.update

May update metadata such as:

title
description
status
branchId
departmentId

Sprint 010 does not replace the physical file through PATCH.

Changing a physical file belongs to future document versioning/replacement
architecture.

All structure assignments must remain tenant-safe.

---

# DELETE /documents/:id

Required permission:

documents.delete

Sprint 010 performs explicit deletion of:

1. physical stored file
2. Document database metadata

The operation must be audited.

Deletion behavior must avoid leaving predictable cross-tenant information.

If storage deletion fails, database metadata must not silently disappear while
the physical file remains unmanaged.

# Tenant Isolation

Every Document query must include:

organizationId

The organization ID must come from trusted organization context middleware.

Never trust organizationId supplied in:

request body
query parameters
route parameters

for authorization scope.

---

# Cross-Tenant Security

The following must fail safely:

- Reading foreign document metadata
- Updating a foreign document
- Downloading a foreign document
- Deleting a foreign document
- Assigning a foreign branch
- Assigning a foreign department
- Discovering foreign documents through search
- Discovering foreign documents through filtering
- Manipulating storage keys
- Supplying arbitrary filesystem paths

Foreign document IDs should generally return:

Document not found

# Security Requirements

Sprint 010 must protect against:

- cross-tenant document access
- path traversal
- arbitrary path selection
- executable uploads
- oversized uploads
- unauthorized downloads
- unauthorized deletion
- foreign structure assignment
- filename-based path manipulation
- accidental absolute-path disclosure
- unsafe trust of organizationId
- direct filesystem access from route handlers

---

# Filename Security

Original filenames are untrusted input.

Examples:

../../secret.txt

..\..\secret.txt

C:\Windows\system.ini

/etc/passwd

must never influence the physical storage destination.

Generate platform-owned stored filenames.

Preserve the original filename only as sanitized metadata.

---

# Storage Key Security

storageKey must be generated internally.

Clients must never submit or update:

storageProvider
storageKey
storedFileName
checksumSha256
sizeBytes

through normal document metadata APIs.

---

# Database Integrity

Recommended relations:

Document -> Organization

Document -> Branch

Document -> Department

Document -> User (uploadedBy)

Organization relations should prevent accidental cross-tenant structure
references.

Use composite organization-aware relationships where appropriate, following
existing Branch/Department integrity patterns.
